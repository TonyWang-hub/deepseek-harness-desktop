## Context

The standalone repository packages one exact, unmodified DSH release and a standard Node sidecar, then compares Electron and Tauri over byte-identical inputs. Reproducibility therefore starts before payload, transport, lifecycle, or candidate code: both candidates must inherit the same root policies, exact dependency graph, commands, CI assumptions, and release inputs.

The sibling `deepseek-harness` checkout is a read-only compatibility oracle. It must never become a workspace member, a file dependency, a lockfile source, a vendored tree, or a path written by a workspace command. Registry dependencies and the checked-in lockfiles must be sufficient for a clean standalone clone.

Use the versions fixed in `plan.md`: standard Node 24.17.x resolved to one exact patch, TypeScript 6.0.3, Rust 1.93.0, Electron 43.4.0, Tauri CLI 2.11.4, Tauri API 2.11.1, and exact DSH 0.1.0-rc.6 family inputs. Pin every external JavaScript and Rust dependency exactly; internal pnpm links may use `workspace:*` because the workspace itself supplies the exact package. Record the exact pnpm release in `packageManager` and commit the lock generated by that release.

The package topology is known now even though later WPs own its source. Create manifests for every planned shared package and for `apps/electron` and `apps/tauri`, including the Tauri Rust manifest. Anticipate the dependency closure described in `plan.md` so later WPs do not need to touch a manifest. If an anticipated dependency is uncertain, resolve it during this WP from the approved architecture and exact published metadata; do not leave floating ranges or defer the manifest edit.

Apply test-first discipline to infrastructure. Before each group of files, run or add the smallest durable validation that demonstrates the missing or invalid state and capture the expected failure. Make the configuration change, then rerun the same validation to green. Do not add product behavior in this WP.

## Risks

- **Premature dependency omission**: A later WP may discover a missing library. Mitigate by deriving every package's dependency closure from all mission WPs and contracts now, then treating any omission as a WP01 planning defect rather than an ad hoc lock edit.
- **False exactness**: Exact top-level specs can still resolve unexpected transitive content. Mitigate with checked-in pnpm/Cargo locks, integrity/checksum review, exact package-manager/toolchain pins, and repeated no-diff installs.
- **Sibling-checkout coupling**: Convenient local links would make builds non-standalone and could mutate upstream. Mitigate with workspace/path scans, CI clean clones, and explicit local-oracle commands owned by later compatibility work.
- **Cross-platform configuration drift**: macOS-only shell syntax can break Windows/Linux neutral jobs. Mitigate with package scripts, explicit shells, and matrix validation from the initial workflow.
- **Rust target incompleteness**: WP10 owns Rust source, so WP01 can prove manifest resolution but not final compilation. Mitigate with explicit target paths, locked `cargo metadata` now, and a reserved full `cargo check --workspace --locked` gate that WP10 must make green.
- **Broad ignore rules**: Payload/evidence ignores can accidentally hide required fixtures or decision artifacts. Mitigate with positive `git check-ignore` assertions for both ignored and deliberately trackable paths.
